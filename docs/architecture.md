# Lurkbox architecture

Lurkbox is a controller-driven TV client for Twitch. The first target is SteamOS Game Mode, where it also has to work as the floating picture of [Floater](https://github.com/jancard/decky-floater). An Android app (Android TV, tablets, phones) is planned from the same codebase.

## Layout

```
packages/core/          @lurkbox/core: the platform-neutral app (browser code only)
  src/index.html, css/, js/, js/views/, fonts/
  src/shared/           config.js (Client ID, scopes), settings.js (defaults, themes, sanitizeSettings),
                        twitch-auth.js, direct.js, clips.js, hls-rewrite.js (host-side Twitch logic, fetch injected)
  src/platform.d.ts     the window.lurkbox interface every host implements
  src/platform-check.js dev check: core use of window.lurkbox == platform.d.ts
  test/                 core unit tests
apps/desktop/           Electron app (SteamOS / Linux): AppImage and Flatpak
  src/main/             main process (Twitch auth, direct playback, Steam, Floater, joydev, ...)
  src/preload.js        the desktop window.lurkbox (contextBridge → ipcMain)
  src/login-preload.js  controller navigation in the twitch.tv login window
  electron-builder.config.js, flatpak/, scripts/ (deploy, steam_shortcut.py)
  test/unit, test/smoke, test/fixtures
assets/                 icons, Steam art and their sources (shared)
docs/                   this file, development.md, android.md
```

npm workspaces tie `packages/core` and `apps/desktop` together; `apps/desktop` depends on `@lurkbox/core`. The Decky companion plugin is a separate repository ([lurkbox/decky-lurkbox](https://github.com/lurkbox/decky-lurkbox)).

## The platform boundary

The core never imports Node or Electron. Everything it needs from the device goes through `window.lurkbox`, documented member by member in [`packages/core/src/platform.d.ts`](../packages/core/src/platform.d.ts): settings, accounts and sign-in, the Helix API (tokens stay in the host), direct playback (GQL and usher, which need CORS-free requests and the twitch.tv session cookie), VOD resume positions, channel points, window focus, open requests, and the desktop-only Steam art, joydev and extension features. Members that only make sense on some hosts are optional and feature-tested by the core.

Two tests keep the boundary honest:
- `packages/core/test/platform.test.mjs` runs `platform-check.js`, which scans the core's `.js` and `.html` for `window.lurkbox` use (direct, `?.`, aliases, destructuring) and fails on a member missing from `platform.d.ts`, on a documented member nothing uses, and on computed access it can't check.
- `apps/desktop/test/unit/preload-platform.test.mjs` fails unless `preload.js` exposes exactly the documented members; `apps/android/test/platform.test.mjs` fails unless the Android platform has every required member and nothing undocumented.

The host also serves two files next to `index.html`: `/vendor/hls.min.js` (from the hls.js dependency) and `/vendor/wordmark.json` (from `assets/src/`).

Shared, platform-neutral logic that a non-browser host also needs lives in `packages/core/src/shared/` as ES modules. The desktop main process loads them with `require()` (require(esm), Electron 45 / Node 24); `apps/desktop/src/main/store.js` re-exports the settings schema next to its JSON file store, and `twitch.js`, `direct.js` and `clips.js` there re-export the shared Twitch modules. The Android platform layer (`apps/android/src/`) imports the same modules and esbuild bundles them into one script; see [android.md](android.md).

## Desktop host (Electron)

- **Why Electron:** the official Twitch embed needs a real Chromium; Electron gives the Gamepad API and lets background throttling be switched off (`backgroundThrottling: false` plus the disable-renderer-backgrounding switches), which Floater needs; it packages as an AppImage and as a Flatpak (`org.electronjs.Electron2.BaseApp`). Alternatives considered: Qt/mpv, and the Android TV app under Waydroid (heavy, uncertain PipeWire capture, awkward with the controller).
- **Serving the core:** `src/main/server.js` serves `packages/core/src` on `http://localhost:<random port>/` (loopback only), because the embed refuses `file://` and needs `parent=localhost`. `src/main/paths.js` finds the core through the `@lurkbox/core` package and the assets in the repo (development) or in `app.asar/assets` (packaged).
- **Packaging:** `apps/desktop/electron-builder.config.js`. Output `dist/Lurkbox-<version>-x86_64.AppImage` at the repo root; app id `io.github.lurkbox.Lurkbox`; productName `Lurkbox`, so user data is in `~/.config/Lurkbox/`. The Flatpak (`flatpak/`, [flatpak.md](flatpak.md)) wraps the electron-builder `dir` output; its user data is in `~/.var/app/io.github.lurkbox.Lurkbox/config/Lurkbox/`, and `flatpak-import.js` copies an AppImage profile there once. electron-builder copies `@lurkbox/core` (its `files`: `src/` without the dev check) and hls.js into `app.asar/node_modules`.
- **Data:** tokens (`tokens.json`, mode 0600, `{accounts, active}`), settings, resume positions (`resume.json`, with each video's details for Continue watching), encrypted per-account player cookie jars, `lurkbox.log` (up to 5 MB, then rotated to `lurkbox.log.1`). Never in the repo.
- **Storage protection:** Lurkbox runs Chromium with its `basic` password store everywhere (Game Mode has no system keyring, and one store keeps the sign-in readable in both Desktop and Game Mode). With that store, the cookie database and the per-account jars are encrypted with a fixed key, not one held by the OS, so the protection boundary is the user's own files: anything that can read `~/.config/Lurkbox/` as the user can use the twitch.tv session and the tokens there. Keep that folder private to the user (the app writes its token and jar files with mode 0600).
- **Page policy:** the renderer's `index.html` has a Content-Security-Policy that limits scripts to the page's own files and Twitch's embed script, frames to Twitch's player, chat and clips, and images, media and connections to the Twitch, 7TV, BTTV and FFZ hosts plus `lbhls:`. A new host means a change to that policy. The server sends `X-Content-Type-Options: nosniff`, and the main process answers renderer IPC only from the window's own page.

## Twitch

- **Sign-in:** Device Code Grant with a public client (no secret). The Client ID and scopes are in `packages/core/src/shared/config.js`; a Client ID saved in Settings overrides it. All scopes are requested once; a token missing any asks for sign-in again.
- **TV sign-in** (`tv-signin.js`, `player-session.js`): twitch.tv/login opens in an in-app window (TV zoom, D-pad → Tab), then the same window shows the Authorize page for the device code; the user presses Authorize. The web login and the API token must be the same user. `planSignIn()` picks consent-only, full, or full-clear (add account / different user). The phone flow is the fallback. Multiple accounts each keep their own encrypted twitch.tv cookie jar.
- **Player:** the default "direct" engine gets a playback token from Twitch's web GQL (`PlaybackAccessToken`) and the usher master playlist in the main process, then plays it with hls.js in a `<video>`. The official embed (`Twitch.Player`) is the automatic fallback and can be forced in Settings. Ads are detected (`EXT-X-DATERANGE`) and labelled, **never skipped or filtered**. Fatal hls.js errors: AV1/HEVC media errors reload once as H.264; H.264 tries `recoverMediaError`, then reloads, then falls back to the embed.
- **Chat:** read over anonymous IRC (`wss://irc-ws.chat.twitch.tv`), with Twitch emotes and badges (Helix) and 7TV, BetterTTV and FrankerFaceZ emotes and 7TV cosmetics (all in the core, plain fetch/WebSocket). An experimental mode loads the real extensions into Twitch's embedded chat (`chat-extensions.js`, desktop only).
- **Chat sending** (`chat-send.js`, `chat-composer.js`, `text-entry.js`): Helix `POST /chat/messages` as the signed-in account (`user:write:chat`, requested with every other scope; a token without it asks for the sign-in again). The message is drawn at once (dimmed) and confirmed when the anonymous IRC connection receives it (matched by Helix's `message_id`, else by sender and text; after 15 s it is marked "not seen in chat yet"). `is_sent: false` marks it "not sent" with a toast of `drop_reason`; a 429 blocks sending until `Ratelimit-Reset`. Room modes come from IRC ROOMSTATE (merged, since Twitch sends only changes after the join) and show above the composer; a local gate keeps a 1 s gap between messages and waits out slow mode unless your own echoed badges say broadcaster, moderator or VIP. The composer's keyboard is Steam's (`openOnScreenKeyboard`, desktop in Game Mode, typing into the focused box like the sign-in window) or the core's own (`osk.js`, with a symbol row for chat). While it has focus, "video only when unfocused" leaves the chat alone, since Steam's keyboard can take the focus. Twitch chat style hides the composer (Twitch's frame has its own input).
- **Sorting** (`shared/sorts.js`, `listSort()` and `sortChip()` in `grid.js`): the sort lists and comparators are pure and shared, so `sanitizeSettings` validates the saved choices (`liveSort`, `streamSort`, `vodSort`, `searchSort`; the older `followSort` is Following → Offline). Every comparator is stable with an A–Z tie-break, so a refresh with equal values doesn't shuffle cards. A view's `onAction` takes Y and calls `cycle()`, which saves the choice, updates the chip and re-sorts with `KeyedGrid.set(items, { keepPosition: true })` (focus stays in the same slot, counting cards only), or `pagedGrid(...).resort()` for a channel's videos. On Following, Y goes to the section that has focus. "By game" adds non-focusable header items (`withGameHeaders()`) that span the grid's row. Sorting is client-side over what has loaded; Browse and categories still load Twitch's top streams by viewers.
- **Channel page** (`views/channel.js`, `shared/channel-page.js`): reached from X on a stream card (`data-channel-*` on the card, `channelOfCard()` in `grid.js`; a touch long-press does the same), offline follows, search results and the player's channel icon (`nav.openChannel()`, which doesn't stack the same channel twice). The header comes from Helix `/users` (avatar, description, `offline_image_url` as the banner; Helix has no profile banner), `/streams` (the LIVE card), `/channels/followers` (`total` only, readable with any user token) and the follow state. Tabs are focusable buttons; LB/RB step through them (the view's `onAction`), and the view keeps its tab across `nav.refresh()`. Videos use Helix `/videos?type=` (archive, highlight, upload) with the VOD sort; clips use `/clips` with `started_at` and `ended_at` from `clipRange()` (both ends, because a missing `ended_at` means "a week after started_at") and the clip sort (`sortClips()`); the schedule uses `/schedule` (a 404 means no schedule), formatted with `fmtSchedule()` in the device's time zone (Today/Tomorrow by that zone's calendar). Filter pills (`filterPills()`) and the sorts are saved settings (`videoFilter`, `clipPeriod`, `clipSort`). Panels and social links have no public API and are left to Twitch's own page (`openChannelPage`); no GQL is used here. The **Emotes** tab (`views/channel-emotes.js`, pure parts in `emote-browser.js`) reuses the chat's loaders and its session cache (`emoteCache` in `emote-providers.js`, now shared) for 7TV, BetterTTV and FrankerFaceZ, and Helix `GET /chat/emotes?broadcaster_id` (`ChannelEmoteCache` in `user-emotes.js`) for the channel's Twitch emotes; all four load at once so each pill shows its count. `shapeEmotes()` sorts A–Z, keeps one per name and marks overlays (7TV/BTTV zero-width, FFZ modifiers); `filterEmotes()` puts prefix matches first. The grid adds 96 cells at a time as the focus or the scroll nears the end; the detail panel follows the focus ring's `lurkbox-focus` event (`markFocused()` in `focus.js`; focusin is deferred while the window lacks OS focus, as under Gamescope) and shows the next CDN size up (`bigUrl()`). A puts the name into a per-channel draft kept in memory (`addToDraft()`), which `Player.openLive()` takes into the composer (`takeDraft()`); Y adds it to the channel's quick-chat list (`addEmotePhrase()`). The image hosts are the chat's, already in the page policy.
- **Clips** (`clip-engine.js`, desktop `clips.js`): Helix `/clips` has no video URL, so the host asks Twitch's web GQL for `VideoAccessToken_Clip` (the persisted query twitch.tv sends, then the plain query if the hash is unknown; anonymous, Twitch's web client ID) and signs each `videoQualities[].sourceURL` with the token's `sig` and `token` (only https URLs on Twitch's hosts). `ClipEngine` plays the chosen MP4 in a `<video>` with the DirectEngine-shaped API, so the overlay, quality pop-over, seek bar and scrubber work unchanged (`kind: 'clip'`); its Auto follows Settings → Player → default quality and the background cap (`pickClipQuality()`). `clipSourcePlan()` falls back to `ClipEmbed` (`clips.twitch.tv/embed?parent=localhost`, no API: its end is timed from the clip's length) when the engine setting is the Twitch player, the host lacks `clipSources`, GQL fails, or the MP4 errors. The player keeps the list a clip came from (`clipList`): LB/RB and the prev/next icons step through it, and ENDED plays the next one (`clipAutoplay`). "Watch from here" opens the clip's `video_id` at `vod_offset` (Helix `/videos?id=` first, so a deleted broadcast says so).
- **Making clips** (`shared/my-clips.js`, `Player.createClip()`): the live overlay's scissors (signed in only) send Helix `POST /clips?broadcaster_id=` through `window.lurkbox.helix` (the token never reaches the page). `clipAuthState()` checks `clips:edit` first (a token without it opens the same "sign in again" dialog as chat). `clipCreateResult()` turns the HelixResult into the clip's id and edit link (only https links on Twitch's hosts are shown or encoded, else `clips.twitch.tv/<id>/edit`) or a code and message: 401/missing scope → sign in again, 403 → clips off or limited, 404 → not live, 429 → blocked until `Ratelimit-Reset`, 5xx → unavailable. The toast holds the host's QR code of the edit link. "My clips" (`myClips` setting: per account, newest first, at most 50, validated by `sanitizeSettings`) shows at the top of the channel's Clips tab; Helix `/clips?id=` fills the cards, and clips Twitch is still processing show as "Processing…".
- **Continue watching** (`shared/continue-watching.js`, `js/continue-watching.js`, the top of `views/following.js`): built on the host's per-account resume positions (desktop `resume.json`, Android preferences, demo in memory). `resumeSet(id, pos, dur, meta)` also stores the video's details (`m`: title, login, name, user id, thumbnail; `sanitizeResumeMeta`, https or the demo scheme only; kept from the last save when left out); `resumeList()` returns the active account's entries and `resumeClear()` forgets them (Settings → Clear watch history). The entry maths (`resumeUpdate`, `resumeEntries`, 300 per account) are shared by both hosts. `continueWatching()` makes the row: at least 30 s watched, not finished (≥ 95 % or under 2 min left, `isFinished`), watched in the last 30 days, a known duration, newest first, at most 20. Each VOD is checked once per account and session with one Helix `GET /videos?id=…` (`checkVideos`): fresh details, or gone (a 404, or missing from a 200), which `resumeSet(id, 0)` forgets; network errors, 401, 429 and 5xx change nothing. A on a card plays from the saved position (`startAt`, so no "Continue watching?" question: picking the card already says "continue"); Remove: X on the focused card (the header's `{X} remove` chip and a badge on the focused card say so; the chip is tappable too), the card's ✕ (a `role=button` span, shown on hover with a mouse and always on the touch layouts as a 44 px target), or the long-press menu (Remove, channel page). The card goes at once and an Undo toast (Y, or its button) lasts ~6 s; `scheduleRemoval()` only forgets the position when that time is up (`flushRemovals()` at exit), so Undo puts the card back unchanged. The row reloads on every Following refresh and right after the player closes (`view.onPlayerClosed()`, called by `nav.closePlayer()`). It's a `KeyedGrid` in a one-row sideways scroller (`.hscroll`): `scrollToFocus()` also scrolls the row (`computeScrollLeft`), the phone layout shows 72 %-wide cards with scroll snapping, and Y does nothing there (the order is fixed). Clips aren't in the row (at most 60 s, always under "2 minutes left").
- **Search history** (`shared/search-history.js`, `views/search.js`): settings `searchHistory` (`{ <user id>: [{ q, at, pick? }] }`, newest first, at most 20 per account, one entry per query ignoring case and spaces, `pick` = the channel or category picked from its results) and `searchHistoryOn`, both validated by `sanitizeSettings` like the emote recents. A search is recorded when something is picked from its results. An empty box shows the active account's list; X on an entry deletes it and keeps the focus slot. Search also queries Helix `GET /search/categories` (one request per search, shown above the channels).
- **On-screen keyboard** (`osk.js`, `osk-layout.js`): a CSS grid of `COLS` (10) equal columns; every key spans whole cells and every row's spans add up to `COLS` (unit-tested), so the columns line up in both layouts (letters, symbols and numbers) and in the chat variant's extra punctuation row. The D-pad doesn't use the spatial search here: the position is `{row, col}`, up/down keep `col` (so leaving a wide key returns to the key you came from) and left/right step one key and wrap within the row (`oskMove()`). Both layouts have the same number of rows, so switching doesn't resize the dialog.
- **Emote picker and quick chat** (`emote-picker.js`, `user-emotes.js`, `quick-chat.js`, `shared/quick-chat.js`): your own emotes come from Helix `GET /chat/emotes/user` (`user:read:emotes`, every page, with `broadcaster_id` for the channel's follower emotes, cached 30 min per account and channel); image URLs come from the response's `template`. They also draw your own messages (the chat's `lookup()`: the channel's emotes, then yours). The picker and quick chat are `Popover`s: from the composer they hang above its buttons on the player screen (`cpop`), and quick chat also above the overlay's icon. `Popover` passes the actions it doesn't use itself to the pop-over's `onAction` (LB/RB tabs, X/Y add/edit). Phrases and recent emotes live in settings (`quickChat`: global list plus lists keyed by broadcaster id with the login kept for display; `emoteRecents`: per account), validated by `sanitizeSettings`. A phrase goes through the same `Chat.send()` with its text as the cooldown key (3 s), behind the slow-mode gate.
- **Layout modes** (`shared/layout-mode.js`, `js/layout.js`, `css/touch.css`): TV (the couch layout), tablet and phone. `pickLayout()` is pure: the Settings choice (`layoutMode`: Auto, TV, Tablet, Phone) wins; Auto is TV unless the host offers touch layouts (`AppInfo.touch`, Android only, so the desktop is always TV), the primary pointer is coarse and no controller is connected; then a window narrower than 700 px or shorter than 500 px on its short side is a phone, anything else a tablet. `applyLayout()` sets `layout-tv|tablet|phone`, `touch-ui` and `orient-portrait|landscape` on `<body>` and re-checks on resize, rotation, controller (dis)connects and setting changes; every rule in `touch.css` hangs off those classes, so the TV layout is unchanged. Phone: a top app bar (`#appbar`: section title, account avatar) and the rail restyled as a bottom tab bar with the same sections; dialogs are bottom sheets. Tablet: the rail (icons only under 1000 px). Touch input is its own input mode (`input-touch`: no focus ring, no controller hints, a tapped button lets go of focus; a long-press's context menu is not Back). Text boxes use the system keyboard (`keyboardFor()` resolves `'system'`) when `useSystemKeyboard()`: a touch layout, a coarse pointer, no controller. Safe areas come from Capacitor's `--safe-area-inset-*` (else `env()`). **The player on touch** (`Player.installTouch()`, `js/touch.js`): in portrait (phone and tablet) the video sits on top at 16:9 and the chat fills the rest with the composer at the bottom (chat starts on); a phone held sideways shows the video full screen and the chat as a panel swiped in from the right (a swipe right puts it away); a tablet in landscape keeps the side panel. A tap toggles the controls, a double tap on the left or right half seeks ∓10 s on VODs and clips (`seekBy()`, with a "−10 s" flash), a swipe down closes the player on a phone; the overlay's icon row scrolls sideways when it doesn't fit; on a phone the pop-overs are bottom sheets and the volume control goes (the phone's buttons). The stage is `touch-action: none` and its mouse click handler ignores the click that follows a touch. **Other gestures:** a horizontal swipe on a channel page steps its tabs (`tabStepForSwipe()`, the same `onAction` as LB/RB; touch events on `#content`, which is `touch-action: pan-y`; the tab strip and pills keep their own sideways scroll); a pull down from the top of Following, Browse, Categories or a channel page refreshes it (`bindPullToRefresh()`, the same `nav.refresh()` as Y); long-press (`onLongPress()`, `LongPress`: 500 ms held still, moving cancels) opens a card's channel page or deletes a recent search.
- **Raids:** EventSub WebSocket `channel.raid` for the watched channel; a countdown that B cancels.
- **Player overlay** (`player.js`, `player-ui.js`, `popover.js`, `slider.js`, `icons.js`): a translucent scrim over the full-bleed video, built once and updated in place so the focused control keeps its node. One row of outline icons (Lurkbox's own 24-px stroke set, `icons.js`); the focused, hovered or long-pressed icon shows a label bubble (`controlLabel()`), with the A glyph only when focused from a controller or keyboard. Volume, quality, chat, channel points and "more" open pop-overs anchored above their icon (`anchorPopover()`); focus moves in, and B closes and returns focus to the icon (`Popover`, by focus key if the bar was re-rendered). The overlay hides after 4 s without input (8 s with a pop-over open) and comes back with focus on the control used last.
- **Chat layout** (`shared/chat-layout.js`, `chat-controls.js`): text size, panel width (Auto or 20–50 % of the window, never more than half, so the video keeps the rest and is letterboxed, never squished), side, background opacity and "over the video" (Lurkbox chat only, and only on the Direct engine: Twitch's chat frame and the embed pause when covered). Height (30–100 % of the player, `chatHeight`) and position (`chatVPos`, top or bottom, shown under 100 %) come from `chatBox()`: `applyChatLayout()` sets `chat-short`/`chat-top`/`chat-bottom` and `--chat-h`, `--chat-top`, `--chat-bottom` on `#player-screen`. Beside the video the panel (and in Twitch chat style the visible `tc-panel` frame) keeps its width at that height, so the video keeps its size; over the video, a bottom chat lifts above the control bar while the overlay is open (the bar's height, re-measured on show, hide and resize). 100 % is the old full-height layout; the hidden points frame and the rewards modal keep their own boxes; the phone layout and touch portrait ignore it (`chatHeightApplies()`). The chat pop-over and Settings → Chat build their controls from the same specs (`chatControlSpecs()`) over the same settings keys. Sliders call `previewSettings()` (state.js), which updates `state.settings` and every listener at once and saves after 250 ms; until then pending values win over host echoes.
- **Twitch chat style:** Twitch's embedded chat page is drawn at desktop size, so the main process zooms it inside the frame (`html { zoom }`, re-applied on every frame load, points scan and setting change) by Settings → Chat → Twitch chat size (Auto = the TV sign-in window's rule, about 1.74 on an 800-px screen; or 75–250 %, also the chat pop-over's text size slider in this style). With the width on Auto the side panel widens to keep ~340 CSS px of chat layout, capped at 45 % of the window; a set width keeps at least 250 CSS px of layout. The video shrinks beside it (`packages/core/src/shared/tv-zoom.js`).
- **Channel points:** Twitch's embedded chat page signed in with the web session; the main process scans the frame, auto-claims the bonus and drives the rewards popover with the controller. Rewards (and Y on a prediction/poll toast) open the **rewards view**: the same chat frame, moved by CSS only (moving an iframe reloads it) into a centred modal of 70 % × 85 % of the screen, with the controller hint in a strip below it. The main process opens Twitch's popover and fits it to the whole frame (`fitRewardsSource()`: fixed to the frame, the boxes down to its scroll container grow, undone on close). B goes back from a reward's detail first (the popover's Back button), then closes the view and focuses the overlay's points icon. Watch-time minutes are reported for the on-screen stream on the direct engine only. The chat frame is a third-party frame of the `http://localhost` page, so it only gets twitch.tv cookies marked `SameSite=None; Secure`: a cookie written Lax or without SameSite (for example by twitch.tv's own scripts in a first-party window, such as the hidden Drops or follow windows) leaves the frame signed out (no balance, no bonus, no rewards button). `keepTwitchCookiesThirdParty()` (`player-session.js`) repairs such cookies at startup and re-sets every later write as `SameSite=None; Secure`, logging names only. The scan reports whether the frame's scripts see an `auth-token` cookie, and opening the rewards retries for 4 s and logs which button strategies found nothing.
- **Drops** (`drops.js`, `views/drops.js`, `js/drops.js`): the Drops section frames Twitch's own inventory page (`www.twitch.tv/drops/inventory`) in the default session; the main process strips `X-Frame-Options` and CSP `frame-ancestors` for that URL only, for sub-frames of Lurkbox's own window, and the iframe is sandboxed without top navigation or popups. The page gets the login window's TV zoom; while the frame has the app's focus, frame-nav runs inside it (B: a dialog's Back, else back to the rail). DOM focus stays on the app's frame host (`domFocus: false`; the ring alone shows the target), because focusing an element inside the frame takes focus from the app, which takes it back (`frame-focus.js`), and the two would take turns. The navigation runs from focus on the frame until focus lands on another control of the app (`views/drops.js`), and frame loads re-prepare it without resetting it (`ensureNavSource`, `drops-frame.js`). Auto-claim (`DropsClaimer`) loads the page in a hidden window of the same session one minute after start and every 15 min (never twice in 5 min; errors double the delay up to 4 h; inert with the setting off or without a twitch.tv session), reads the campaigns (tolerant selectors: `.inventory-campaign-info`, `role=progressbar`, Claim buttons by `data-a-target`/`aria-label` or text) and clicks at most 5 Claim buttons, 1.5 s apart, stopping when the page doesn't take one. The player's drops chip comes from the last check's campaigns for the stream's game; there is no reliable public "drops enabled" signal.
- **Subscriptions and blocks** (`social.js`, pure with Helix injected; `social-ui.js` wires it in): Helix has no list of your subscriptions, so `SubChecker` asks `GET /subscriptions/user?broadcaster_id&user_id` (scope `user:read:subscriptions`) for each followed channel, two at a time with a 250 ms gap per worker, deduplicated, and caches each answer (subscribed or a 404 "not subscribed") per account and channel for an hour; other errors aren't cached, and a 429 pauses until the reset (≤ 60 s) and retries once. Following paints a `.badge.sub` on the cards from that cache (`paintSubBadges()` after every repaint); Settings → Account → Subscriptions (`subscriptionsView()`) shows tier (`tierLabel()`: 1000/2000/3000 → Tier 1/2/3) and gifter. `BlockList` loads `GET /users/blocks?broadcaster_id=<me>` (all pages) when chat joins a channel or the account changes, and is updated in place by `PUT /users/blocks?target_user_id&source_context=chat` and `DELETE /users/blocks?target_user_id` (scope `user:manage:blocked_users`); both go through `confirmBlock()` / `confirmUnblock()`, which send nothing without a "Yes". The chat drops a blocked user's messages in `onMessage()` (`hideFromChat()`, setting `hideBlockedChat`) and removes ones already shown when the list changes. The user card (`openUserCard()`) opens from a click on a `.chat-nick`, or in the player from a line picked with Up from the composer (`Player.startLinePick()`: Up/Down step lines, A opens the card, B or Down past the newest line goes back; the list doesn't auto-scroll meanwhile). Demo mode answers both endpoints (`demo/helix.js`: five subs, one of them gifted, and three blocked users, two to a page).
- **Follow / unfollow** (`follow.js` in the core and in the main process): the public API dropped follow/unfollow in 2023, so on the user's press (unfollow only after Lurkbox's own confirmation dialog) the main process loads `www.twitch.tv/<login>` in a hidden window of the twitch.tv session, checks that it is that channel's page (path and header h1), finds the header's button (`data-a-target` follow-button / unfollow-button, then `aria-label` naming the channel, then text), clicks it (and Twitch's `modal-unfollow-button` dialog) and waits for the button to flip. A page without a button or without a flip gets one retry in a fresh window; a captcha, the sign-in wall or another channel's page get none. Failures offer the channel page in the in-app twitch.tv window (`createLoginWindow`). The initial state is Helix `GET /channels/followed?user_id=&broadcaster_id=`; success invalidates the follows caches.
- **Controller in twitch.tv pages** (`frame-nav.js`, shared by the sign-in window, the rewards view and the Drops section): spatial navigation over single actionable elements. Focusable wrappers that contain other targets and anything over ~60 % of the viewport are skipped; the focus ring follows the element's rect (divided by the page's CSS zoom, clipped to its scroll containers and the frame) and is redrawn on scroll, resize and every 250 ms; the focused element is scrolled into view (nearest) inside its own scroll containers only, never the page hosting the frame. A on a text box opens Steam's keyboard.
- **Unofficial interfaces** (web GQL, usher, the embedded chat page, the Drops inventory page, "minute-watched") are listed with their off switches in the README. Twitch's private GQL is not used to follow, subscribe or change the account; follow/unfollow press Twitch's own button on its page.
- **What the public API can't do for viewers:** follow/unfollow, channel points balance and redemptions, voting in predictions/polls, subs, gifts, Bits, Drops.

## SteamOS and Floater (desktop only)

- **Never pause on blur/visibilitychange,** no exclusive fullscreen, readable at 10–50 % scale. While unfocused for 1.5 s the player hides chat and controls ("video only"); after 3 s the quality can be capped (Settings).
- **Audio scope (`keep-scope.js`):** Chromium moves the browser process into `app-<desktopName>-<pid>.scope` on its first portal request, which pulls new children (the audio service included) out of Steam's `app-steam-app<appid>` scope, so Floater would find no audio. Lurkbox records the launch scope and writes its pids back into it (`LURKBOX_KEEP_SCOPE=0` turns it off).
- **VA-API (`gpu-diag.js`):** decoder profiles come from a hidden chrome://gpu window, the decoder in use from the DevTools Media domain. `--ozone-platform=x11` is only appended without `WAYLAND_DISPLAY`; prefer setting it in the Steam launch options.
- **Controllers:** the Gamepad API plus a joydev reader (`joydev.js`) for pads Chromium misses; input is ignored while unfocused unless enabled in Settings.
- **Steam library art:** the core renders themed SVG/PNGs; `steam-art.js` writes Steam's grid files (with a one-time backup) and, when Steam's CEF debugger is on, calls only allow-listed `SteamClient.Apps` functions.
- **Decky plugin bridge:** `notify-export.js` writes which followed channels have the bell on (`notify-channels.json`); `open-request.js` consumes `open-request.json` from the plugin to open a channel.

## Decisions

- Direct HLS playback is the default engine (a ToS grey area); the embed is the fallback.
- No ad skipping or filtering.
- PiP mode was removed; Floater does the floating and the player hides its chrome while unfocused.
- Screen margin defaults to 0 (a margin made the embed's visibility check pause playback).
- Settings live in the app's own UI.
- The UI follows the official Android TV app's navigation model (rows, focus, overlay, chat side panel) without copying its code or assets.
- Core UI work stays touch-ready, for the Android app.
